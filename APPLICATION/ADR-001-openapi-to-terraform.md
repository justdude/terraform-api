# ADR-001: Локальная конвертация OpenAPI → Terraform (Azure API Management) без LLM

**Status:** Proposed
**Date:** 2026-06-14
**Deciders:** Ivan (автор), ревьюер инфраструктуры
**Context-tags:** Azure APIM, OpenAPI 3.0, Terraform, детерминизм, без облака

---

## Context

Есть 10 API в Azure API Management. OpenAPI-спеки (в основном 3.0, JSON и частично
YAML) нужно периодически обновлять и держать Terraform-конфигурацию актуальной.
Файлы спек уже могут существовать; нужно уметь как обновлять их (добавлять/удалять
методы), так и генерировать с нуля.

Ограничения и силы, которые влияют на решение:

- **Без LLM.** Преобразование должно быть детерминированным и воспроизводимым.
- **Низкое количество ошибок.** Результат должен проходить валидацию автоматически.
- **Лёгкость использования.** Минимум шагов, минимум внешних зависимостей.
- **Нет доступа к Azure CLI и к самому Azure.** `terraform apply` выполняется в
  CI или коллегой с доступом; локально доступны только `init/fmt/validate/console`.
- Ключевой факт об APIM: ресурс `azurerm_api_management_api` с блоком `import`
  принимает **всю спеку целиком** через `content_value`, и APIM сам разворачивает
  все операции. То есть «методы» не обязаны существовать как отдельные
  Terraform-ресурсы — управлять ими можно на уровне OpenAPI-файла.

Из этого факта следует главный архитектурный вывод: **задача «добавить/удалить
метод» сводится к детерминированному редактированию OpenAPI-файла, а не к
генерации Terraform по каждому методу.** Это радикально снижает поверхность ошибок.

---

## Decision (кратко)

**OpenAPI-файл — единственный источник истины.** Методами управляет тонкая
детерминированная CLI-утилита (`apitf`: `init/add/remove/list/validate/gen`).
Terraform потребляет спеку целиком через `import { content_value = file(...) }`
(Вариант 1). Где нужен коммитимый per-API Terraform — генерируется `.tf.json`
из словаря (Вариант 5), без ручного HCL-шаблонирования. Корректность гарантирует
валидационный шлюз (Вариант 10): `openapi-spec-validator` + `terraform validate`.

Это сочетание Вариантов **1 + 5/6 + 7 + 10**. Обоснование — ниже, с результатами
прогона MVP каждого варианта.

---

## Options Considered — 10 итераций с MVP

Каждый вариант прототипировался и (где применимо) прогонялся в песочнице с
Terraform 1.9.8 и Python 3.10. Вердикты подкреплены эмпирикой (см. раздел
«Benchmark»).

### Вариант 1 — Bulk import: спека как источник истины через `file()`
TF ссылается на весь файл; APIM разворачивает операции сам.
**MVP:** рабочий (это доставленный ранее проект `apis-disk.tf`/`apis-url.tf`).
| Сложность | Ошибки TF | UX | Вердикт |
|-----------|-----------|----|---------|
| Низкая | Минимальные (1 ресурс на API) | Высокая | ★ ядро решения |
Pros: меньше всего Terraform-кода и состояния; обновление = заменить файл.
Cons: гранулярность «весь API», не отдельная операция (для APIM это норма).

### Вариант 2 — Кодоген per-operation (`azurerm_api_management_api_operation`)
Скрипт эмитит по одному TF-ресурсу на каждый метод.
**MVP:** возможно, но даёт ×N ресурсов, дублирует то, что APIM уже делает из
импорта; растёт state и риск дрейфа; нужно следить за уникальностью operationId.
**Вердикт:** отклонить как основной. Применять только если нужны
per-operation политики/настройки, которых нет в спеке.

### Вариант 3 — Шаблоны (Jinja2/Handlebars) → HCL
OpenAPI → модель → рендер `.tf` строками.
**MVP:** работает, но строковое шаблонирование HCL провоцирует баги экранирования
кавычек, переносов, спецсимволов в путях/описаниях.
**Вердикт:** хуже Варианта 5 (JSON генерируется из структуры, а не из строк).

### Вариант 4 — CDK for Terraform (cdktf)
Программное описание ресурсов с синтезом в JSON.
**MVP:** тяжёлая зависимость (node/python + cdktf), кривая обучения, избыточно для
плоского импорта спеки.
**Вердикт:** отклонить по критерию «легко пользоваться».

### Вариант 5 — Генерация `.tf.json` из словаря
`json.dumps(dict)` → Terraform читает `.tf.json` нативно. Нет HCL-экранирования.
**MVP:** PASS — сгенерированный файл валиден, Terraform его читает (T5, T7).
| Сложность | Ошибки | UX | Вердикт |
|-----------|--------|----|---------|
| Низкая | Очень низкие (корректность по построению) | Высокая | ★ цель кодогена |

### Вариант 6 — Чистый Terraform: `jsondecode(file)` + `for_each`
Без внешнего кода вообще: Terraform сам читает спеку и перечисляет методы.
**MVP A:** PASS — из спеки нативно получено 3 операции (paths × methods через
`merge([... for ...]...)`).
**Вердикт:** ★ сильный для перечисления/проверки; логика ограничена выразительностью HCL.

### Вариант 7 — Тонкая CLI (`init/add/remove/list/validate/gen`)
Детерминированный редактор OpenAPI на Python (`json`/`ruamel.yaml` +
`openapi-spec-validator`).
**MVP B:** все тесты PASS (детерминизм, обратимость, идемпотентность, валидация,
YAML).
| Сложность | Ошибки | UX | Вердикт |
|-----------|--------|----|---------|
| Низкая | Очень низкие (идемпотентно + валидатор) | Очень высокая | ★ лучший UX для add/remove |

### Вариант 8 — Инкрементальный патчер TF по diff
Парсить старый TF, патчить только изменённое.
**MVP:** высокая сложность, хрупкость парсинга HCL.
**Вердикт:** отклонить — не нужен, т.к. регенерация детерминирована и идемпотентна
(дешевле перегенерировать целиком, чем патчить).

### Вариант 9 — Склейка готовых CLI (jq/yq/openapi-generator) через Makefile
Минимум собственного кода, оркестрация существующих инструментов.
**MVP:** `jq` есть, `yq` отсутствовал в среде; на Windows портируемость хуже.
**Вердикт:** хороший запасной вариант, но «зоопарк» внешних бинарников вредит
критерию «легко». Один Python-скрипт переносимее.

### Вариант 10 — Валидационный шлюз
`openapi-spec-validator` (спека) + `terraform fmt/validate` (конфиг) как гейты в
pre-commit/CI.
**MVP:** PASS — поймал 2 класса ошибок: отсутствие `responses` и битый JSON; ранее
поймал необъявленный path-параметр `{id}`.
**Вердикт:** ★ обязательный сквозной слой, не самостоятельное решение.

## Benchmark — эмпирические результаты MVP

Прогон в песочнице (Terraform 1.9.8, Python 3.10, openapi-spec-validator):

| # | Проверка | Результат |
|---|----------|-----------|
| A | Чистый TF: `jsondecode` перечисляет методы спеки | PASS (3 операции) |
| T1 | Генерация с нуля детерминирована (байт-в-байт при повторе) | PASS |
| T2 | Обратимость: add X → remove X == исходник (байт-в-байт) | PASS |
| T3 | Идемпотентность add: добавить дважды == добавить один раз | PASS |
| T4a | Валидатор ловит отсутствие `responses` | PASS |
| T4b | Валидатор ловит битый JSON | PASS |
| T4c | Валидатор ловит необъявленный path-параметр `{id}` | PASS (исправлено в `add`) |
| T5 | `.tf.json` корректен по построению (без HCL-экранирования) | PASS |
| T6 | YAML: init/add/validate + round-trip байт-в-байт | PASS |
| T7 | Terraform читает `.tf.json` нативно | PASS |

Вывод: связка «детерминированный редактор + валидатор + bulk import / .tf.json»
эмпирически удовлетворяет всем трём критериям (легко, без LLM, мало ошибок).

## Trade-off Analysis

- **Гранулярность управления.** Управление методами на уровне OpenAPI (Варианты
  1/5/6/7) против per-operation TF-ресурсов (Вариант 2). Для APIM импорт спеки уже
  разворачивает операции — per-operation TF добавляет state и риск дрейфа без
  выгоды. Выбираем уровень OpenAPI.
- **Кодоген строками против структуры.** Шаблоны HCL (Вариант 3) хрупки на
  экранировании; `.tf.json` из словаря (Вариант 5) корректен по построению.
  Выбираем `.tf.json` там, где TF нужно коммитить; иначе вообще без кодогена
  (Вариант 6 / `file()`).
- **Свой код против зоопарка CLI.** Один переносимый Python-скрипт (Вариант 7)
  против jq/yq/Make (Вариант 9). Для Windows и «легко пользоваться» один скрипт
  выигрывает; jq/yq остаются опциональным fallback.
- **Регенерация против инкрементального патча.** Поскольку генерация детерминирована
  и идемпотентна (T1–T3), полная перегенерация проще и безопаснее diff-патчинга
  (Вариант 8 отклонён).
- **Тяжёлые фреймворки.** CDKTF (Вариант 4) даёт типобезопасность ценой зависимостей
  и обучения — избыточно для плоского импорта.

## Consequences

Что становится проще:
- Обновление API = одна команда (`apitf add/remove`) либо правка файла + `validate`.
- Terraform-слой почти не меняется: один ресурс на API, спека приходит через `file()`.
- Полностью локальная отладка без доступа к Azure (`validate`, `console`).
- Детерминизм → чистые диффы в git, предсказуемые ревью.

Что становится сложнее / о чём помнить:
- Нужна одна Python-зависимость окружения (`ruamel.yaml`, `openapi-spec-validator`).
  Митигируется `requirements.txt` или упаковкой в один бинарь (pyinstaller).
- Per-operation тонкие настройки APIM (отдельные политики на операцию) не
  выражаются на уровне bulk import — для них точечно добавляется Вариант 2.
- `terraform validate` против схемы `azurerm` требует скачивания провайдера
  (в изолированной среде это бывает медленно); в обычной сети проблемы нет.

Что пересмотреть позже:
- Если появятся per-operation политики — ввести опциональный генератор Варианта 2.
- Если команда уйдёт от Python — портировать CLI на .NET (та же логика: парсер +
  валидатор + сериализация), интерфейс не меняется.

## Recommended Architecture

```
                  ┌────────────────────────┐
   источник истины│   OpenAPI 3.0 (per API)│  specs/<api>.<env>.(json|yaml)
                  └───────────┬────────────┘
                              │
        ┌─────────────────────┼──────────────────────┐
        ▼                     ▼                       ▼
  apitf add/remove      apitf validate           terraform
  (детерм. правка)      (openapi-spec-           consume:
  + авто path-params     validator)              ├ file() bulk import  (Вариант 1)
        │                     │                  ├ .tf.json gen        (Вариант 5)
        └──────── git ────────┘                  └ jsondecode native  (Вариант 6)
                              │
                       pre-commit / CI
                  apitf validate && terraform validate   (Вариант 10)
```

Поток: правите методы через `apitf` (или руками) → `apitf validate` → коммит →
CI запускает `terraform validate` и затем `apply` (там, где есть доступ к Azure).
